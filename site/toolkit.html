A dry run validates software structure. It does not demonstrate an effect, prove provider isolation, or authorize a real study.

  1. 01

    Understand the design.

    Read the protocol, scientific objections, and the study runbook before configuring a run.

    Study runbook ↗
  2. 02

    Inspect the configuration.

    Use the toolkit’s deterministic research allocator. Pin the provider, exact model, reasoning effort, sampling settings, tasks, and memory policy.

    Dry-run example configuration ↘
  3. 03

    Validate the boundaries.

    Test state isolation, corpus hashes, trace completeness, context assembly, and blinded export. A local dry run makes no inference calls. The current trace schema is diagnostic; a validated live trace contract and provider adapter remain prerequisites.

    Diagnostic trace schema ↘
  4. 04

    Freeze before collecting.

    Complete the pilot launch gates. Preregister confirmatory hypotheses, analysis, exclusions, and a justified sample size before confirmatory data collection.

    Preregistration draft ↗
